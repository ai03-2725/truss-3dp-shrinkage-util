# Truss Calibrator v1 — implementation plan

Source of truth: [`PRD.md`](./PRD.md). Implement in `truss-webui/`; follow [`project-structure.md`](./project-structure.md) where it does not conflict with the PRD. This is a delivery checklist, not a request to add extra features. **Depends on** lists prerequisite task IDs; a parent task is complete only after all its subtasks are complete. Work in numerical order unless a dependency explicitly permits otherwise. Every subtask feeds a subsequent subtask or its parent deliverable; task 9 is the release gate.

- [ ] **1. Establish a clean, embeddable baseline.** Depends on: none. Deliverable: a minimal Solid app that builds, uses the provided styles, and can resolve its assets without a site-root assumption.
  - [ ] **1.1. Verify the starting point.** Depends on: none. Run the existing `truss-webui` install/build scripts, inspect `src/App.tsx`, `src/index.tsx`, `index.html`, CSS imports, and Vite config; record any baseline failure before modifying files.
  - [ ] **1.2. Replace demo UI and CSS.** Depends on: 1.1. Remove the Vite/Solid demo markup and its demo-only CSS/assets. Import `src/styles/global.css` for the standalone entry, add only app-specific `truss-`-prefixed styles in `src/local.css`, and render a minimal home screen. Do not introduce a router or CSS reset.
  - [ ] **1.3. Prove portable asset URLs.** Depends on: 1.2. Resolve an existing guide image and the Quad/Single STL files through Vite-managed URL imports rather than `/...` links. Configure the build only as needed so both assets and standalone entry work at a nested URL; leave the Dual STL out. Keep the Solid app exportable for a host page to mount without relying on `window.location`.
  - [ ] **1.4. Check the baseline.** Depends on: 1.3. Run `pnpm build` in `truss-webui` and manually open the minimal app from a nested path; verify the example image and STL download resolve. Fix any asset-path issue before adding the flows.

- [ ] **2. Implement and test the numerical rules.** Depends on: 1. Deliverable: small pure functions shared by both flows and printer management; no UI or persistence required yet.
  - [ ] **2.1. Define minimal data shapes.** Depends on: 1.4. Type a saved printer (`name`, `extrapolationFactor`), a flow's draft strings/checkboxes, and X/Y/A/B inner/outer readings. Preserve raw input strings until validation so partial typing and refreshes work.
  - [ ] **2.2. Validate inputs and warnings.** Depends on: 2.1. Accept finite positive decimal inputs with a period, arbitrary precision, and no comma; reject blank/non-numeric/zero/negative values. Implement non-blocking warning checks for readings outside 135–142 mm, an inner/outer gap **> 0.4 mm** per beam, current XY percentage outside 90–110%, and manually entered printer factor outside 0.9–1.1. Normalize names by trimming and comparing case-insensitively.
  - [ ] **2.3. Calculate and format results.** Depends on: 2.2. Implement the PRD's 8-reading Quad average, X average, unadjusted printer factor, Quad/Single shrinkage (`/ 140`), and `currentXYPercent × shrinkage`. Keep raw numbers for math and storage; round only the displayed shrinkage (up to 10 decimals) and final percentage (4 decimals).
  - [ ] **2.4. Add runnable automated tests.** Depends on: 2.3. Cover sample Quad and Single math, full-precision factor reuse, display-only rounding, rejected inputs, and warning boundaries (including exactly 0.4 versus greater than 0.4). Use Node's built-in test/assert runner if the project's supported Node version permits TypeScript tests; do not add a testing dependency without a need.

- [ ] **3. Build printer data and JSON portability.** Depends on: 2. Deliverable: tested operations for managing printer profiles without requiring screens.
  - [ ] **3.1. Implement printer-list operations.** Depends on: 2.4. Add, rename/edit, replace an existing factor, and delete using trimmed case-insensitive names; reject empty/duplicate names outside the explicit Quad-overwrite path. Require a finite positive factor for manual add/edit; never silently default it to 1. Preserve full numeric precision.
  - [ ] **3.2. Implement versioned export/import.** Depends on: 3.1. Serialize `{ "version": 1, "printers": [...] }`. Validate the **whole** file (JSON shape, supported version, unique non-empty names inside the file, finite positive numeric factors) before changing saved data. On conflicts with local profiles, retain the local ones and return skipped **names and count** while importing the rest.
  - [ ] **3.3. Test data boundaries.** Depends on: 3.2. Test case-insensitive/whitespace conflicts, Quad overwrite versus manual duplicate rejection, unchanged data on invalid or unsupported import, within-file duplicates, valid local conflicts with skip reporting, and export/import precision. Keep this logic independent of browser file-picker UI.

- [ ] **4. Add root state, flow navigation, and persistence.** Depends on: 3. Deliverable: functional home/navigation and safe resume behavior, with placeholder step content until the guided pages are built.
  - [ ] **4.1. Shape the root state.** Depends on: 3.3. Keep saved printers, skip-equipment preference, current screen/flow/step, selected printer, and draft input/checkbox strings in the top-level Solid component. Pass only needed values and actions to screen components; allow transient modal/input state locally. Use screen state, not pathname routing.
  - [ ] **4.2. Load and save browser data safely.** Depends on: 4.1. Restore an unfinished flow on load (including partial fields); save every change to draft fields, checkboxes, step, profiles, and preference. Validate restored data enough to avoid a broken screen; handle read/write/JSON failures without crashing, retain usable in-memory state, and display a storage warning. Do not send data to a server.
  - [ ] **4.3. Implement navigation semantics.** Depends on: 4.2. Provide home choices for Quad, Single, and printer management. Block Single entry with the Quad/import explanation when no printers exist. Provide Back before final results, a confirmed Exit that clears the active flow, and Finish that clears it without deleting printers. Disable Back on either final result; skip equipment confirmation on later Quad runs when the preference is set.
  - [ ] **4.4. Test resume/clear/failure behavior.** Depends on: 4.3. With an injectable/fake storage surface or equivalent small test seam, verify reload of a mid-step draft, refresh and later reopen, preference retention, confirmed exit/finish clearing only active progress, malformed stored data handling, and failed writes while continuing in memory. Manually smoke-test one refresh in the app.

- [ ] **5. Build Manage printers.** Depends on: 4. Deliverable: a usable profile list and backup/restore path before either calibration flow is complete.
  - [ ] **5.1. Show and edit profiles.** Depends on: 4.4. Render printer names and factors in a responsive list/table. Implement add and edit dialogs with required name/factor, duplicate detection, blocking invalid values, and non-blocking factor-range warning; preserve full-precision saved factor.
  - [ ] **5.2. Handle destructive actions.** Depends on: 5.1. Confirm deletion; update the root printer list and persistence on add/edit/delete. Keep the root's storage-failure warning visible where relevant.
  - [ ] **5.3. Wire import/export.** Depends on: 5.2. Offer JSON download and file selection; invoke task 3's validator before merging. Explain invalid/unsupported files without a partial import, and show the count **and names** of skipped local-name conflicts after a valid import.
  - [ ] **5.4. Expose the equipment preference and check the screen.** Depends on: 5.3. Add the skip-equipment toggle at the bottom. Manually verify add/edit/delete, imports, exports, the toggle, and keyboard use on this screen. Printer backup does not include the active flow or preference.

- [ ] **6. Implement the full Quad flow.** Depends on: 5. Deliverable: a user can calibrate, save/overwrite a printer, and apply the slicer result without opening the manual guide.
  - [ ] **6.1. Build prerequisite steps.** Depends on: 5.4. Present all three equipment checks (unless previously skipped) and the three filament-tuning checks, with their guide explanations. Gate Next until each required set is checked; make the Don't ask again option available after equipment checks are satisfied.
  - [ ] **6.2. Build slice, print, and locate steps.** Depends on: 6.1. Include the Quad STL download, seam-placement advice and diagrams, cooling/removal warnings, and the labeled X-beam photo. Use portable imported asset URLs; keep manual text and images available within the flow.
  - [ ] **6.3. Collect X measurements.** Depends on: 6.2. Show outer/inner diagrams, photos, top-entry and correct/incorrect jaw positioning, light-force and parallel-alignment cautions. Label inputs in mm; persist drafts as typed. Block invalid inputs; display only this screen's applicable non-blocking length and **> 0.4 mm gap** warnings.
  - [ ] **6.4. Collect Y, A, and B measurements.** Depends on: 6.3. Clearly label all six remaining outer/inner inputs, retain earlier X values on Back, and apply identical validations and per-beam warnings. Require all eight valid lengths before calculation.
  - [ ] **6.5. Save the printer at the naming step.** Depends on: 6.4. Compute the factor from all eight measurements without a skew exception or rounding. Warn on a trimmed/case-insensitive name match; ask for explicit overwrite confirmation on Next with wording about losing the old factor. Commit the profile on proceeding to results. Track whether this particular save failed so the result can offer its manual-recording fallback.
  - [ ] **6.6. Build Quad results.** Depends on: 6.5. Display shrinkage (up to 10 rounded decimals), current XY input defaulting to 100 with live four-decimal recommended percentage and non-blocking 90–110% warning, and the OrcaSlicer/Bambu Studio application instructions. Normally hide the printer factor; if saving failed, show its full-precision value and prompt the user to note it manually. Do not repeat the per-beam gap warning here. No Back; Finish clears the flow.
  - [ ] **6.7. Walk through both save paths.** Depends on: 6.6. Manually complete a fresh Quad flow, a same-name recalibration with cancel and confirm, a mid-flow refresh/Back, an Exit, and a simulated storage failure. Check that saved values match the test math and the correct fallback appears.

- [ ] **7. Implement the quick Single flow.** Depends on: 6. Deliverable: a two-measurement calibration against an existing printer factor.
  - [ ] **7.1. Select a printer and confirm filament tuning.** Depends on: 6.7. Show saved printers; require a selection and the three tuning checkboxes. Preserve selection on refresh/Back. Do not ask equipment questions or accept a factor manually in this flow.
  - [ ] **7.2. Build slice/print guidance.** Depends on: 7.1. Provide the Single STL, seam guidance, print and cooling/removal instructions, and relevant images from the Single guide using portable asset URLs.
  - [ ] **7.3. Collect the two X readings.** Depends on: 7.2. Include the inner/outer diagrams/photos and complete caliper-placement cautions within the app. Apply the same positive-number gates, 135–142 mm warning, and **> 0.4 mm** pair warning used in Quad; keep warnings on the input screen only.
  - [ ] **7.4. Build Single results.** Depends on: 7.3. Apply the selected saved factor to the X average before dividing by 140, retain full precision until display, default the current XY input to 100, and show the rounded percentage plus slicer instructions. Allow Finish, not Back, from results.
  - [ ] **7.5. Check the end-to-end quick flow.** Depends on: 7.4. Complete a run with a freshly saved printer and one imported printer; confirm correct selection/factor after a refresh, changed current XY values, warning behavior, Exit, and Finish.

- [ ] **8. Polish content, responsive UI, and accessibility.** Depends on: 7. Deliverable: both guided flows are readable and operable across target devices and assistive input.
  - [ ] **8.1. Make layouts responsive.** Depends on: 7.5. Style the step layout, long instructions, diagrams, measurement fields, action buttons, and printer list for desktop/tablet/phone in prefixed `local.css`. Preserve provided global styles and avoid host-site selectors or path assumptions.
  - [ ] **8.2. Make interactions accessible.** Depends on: 8.1. Ensure correct labels, units, error associations, warning announcements, image alt text or appropriate decorative marking, meaningful headings, keyboard navigation, visible focus, and accessible modal focus/return behavior. Check touch targets and contrast against WCAG 2.2 AA.
  - [ ] **8.3. Audit guide coverage.** Depends on: 8.2. Compare each screen against `Documentation/0-Start-Here.md`, `1-Quad-Calibration.md`, and `2-Single-Calibration.md` for missing photos or substantive warnings (seams, cooling, force, jaw orientation). Keep the original voice where practical; make non-Orca/Bambu applicability clear.
  - [ ] **8.4. Perform device/accessibility checks.** Depends on: 8.3. Use narrow and wide viewports, keyboard-only traversal, and a screen reader for at least forms/warnings/dialogs. Resolve issues before the release pass.

- [ ] **9. Validate and document release readiness.** Depends on: 8. Deliverable: verified production build and instructions for deploying both supported forms.
  - [ ] **9.1. Run automated gates.** Depends on: 8.4. Run the math/validation/import/storage tests and `pnpm build`; fix failures, then rerun both. Confirm no test relies on rounding stored factors.
  - [ ] **9.2. Exercise the PRD acceptance scenarios.** Depends on: 9.1. On current desktop Chrome/Firefox/Safari/Edge and mobile Chrome/Safari as available, verify Quad, Single, no-saved-printer guard, overwrite, import failures/conflicts, Back/Exit/Finish, refresh/reopen, warnings, and denied local storage. Record any browser/device not actually checked rather than claiming coverage.
  - [ ] **9.3. Verify both delivery modes.** Depends on: 9.2. Test a production standalone build at a nested URL **and** mount the Solid app on a nested-path host page (Astro if available) with the parent global stylesheet. Verify images, STL downloads, styles, no pathname routing, and that app code sends no printer/measurement data over the network. Separate origins need not share storage; test JSON transfer instead.
  - [ ] **9.4. Document and sign off.** Depends on: 9.3. Update `truss-webui/README.md` with build/run, standalone and embedded mounting/styling/asset requirements, browser-only storage and import/export limitations, and test commands. Compare shipped behavior to [`PRD.md`](./PRD.md); mark the release gate complete only when remaining gaps are fixed or explicitly accepted.
