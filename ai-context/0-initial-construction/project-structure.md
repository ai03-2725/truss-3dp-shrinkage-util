# Planned project structure and context

## Context 
The structural goal of this project is to remain as simple as possible.  
Neither the code nor the contents (instructions, writing, etc) will see major changes once complete; as such, frameworks, templates, and components designed for flexibility of reuse and growth are completely unnecessary.  
Copy duplication is fine as well, since at most there will be two locations to adjust copy (the single and quad calibration flows).  
In this context, more complex and state is more difficult to modify and maintain than more one-off page components; such components/state should be kept to a bare minimum.  

This app should be able to function both standalone (deployed by itself to a subdomain or similar) and embedded into a page (very likely an Astro Island in an Astro website).  
The app does not need to generate CSS resets or similar, as no conflicting styles will be generated by or applied by the parent component.  
The stylesheet provided in `/truss-webui/src/styles/global.css` are what is applied on the parent website; it should be loaded by the standalone version's HTML as well for consistency.  
If any additional styles are required, they should be added to the same `global.css` file if the styling is for a component which can be used on other projects, or in a separate `local.css` if the style is so specific to this one project that it cannot be reused elsewhere.
All `local.css` style classes/IDs should be prefixed with `truss-` to avoid conflict with parent CSS.

As the app may be embedded into part of a larger website and might not be able to tap into browser paths, the app should not use any sort of browser path based router.  

The app should be kept as simple as possible - if adding any features beyond what this structure document covers, ask before implementing or increasing the scope.  


## Planned structure  
This is my current planned architecture for the project; it may be necessary to change this due to not having validated that this is practical or possible, but should serve as a guideline for how simple to keep the project.  
- A top-level solid.js component which acts as the entrypoint and state manager
  - A signal for the current screen/page being displayed
  - A signal which keeps track of user-entered measurements, which are updated by child screens as necessary and cleared upon starting a fresh calibration flow 
  - A signal which keeps track of saved printers in pairs of names and extrapolation factors; this list is loaded upon opening the app and re-saved to the browser's local storage whenever it is updated
  - Setters passed to children components to update state (for example for changing the current screen for navigating to the next page), and in turn any applicable signals passed to children to be displayed or processed
- A set of screen components which act as pages for the user to navigate through:
  - A main menu screen with buttons for starting a calibration flow or editing saved printers
  - A set of pages for the calibration flow documented in `./flow-outline.md`
    - Each page component should be mostly self-contained, returning everything the page displays (titles, text content, images and diagrams, buttons, etc.); this keeps each page's contents and layouts easily modifiable by hand if necessary.  
      I don't expect child components to be necessary much at all.  
  - A page for editing saved printers:
    - A table with columns for the printer name, extrapolation factor, and edit/delete buttons
    - Buttons for adding a new printer, exporting the saved printers as a JSON, and importing saved printer JSONs
      - When importing JSONs, if a printer already exists with the same name, retain the one currently saved and ignore the one incoming from the JSON
    - An edit modal upon selecting a printer to edit; the name and extrapolation factors should be modifiable
    - A delete confirmation modal upon selecting a printer to delete

Some expectations are:
- No component other than the top-level component should need to store any long-term/complex state or signal.
  All the children screens should need to do most of the time is to display what the root component stores, derive calculations from the root component's state, or update the root component's state.
  At most the children components might hold some state for currently typed inputs, keeping track of modal open/closed states, holding temporary values for editing settings, etc.  
- The flow and wording of the original documentation files in `/Documentation` have been very carefully thought out and considered, and should be respected where possible when creating the calibration flow pages.  
  If new writing/copy needs to be generated, match the voice of the original writing if possible.  
- As stated multiple times, simplicity is key.
  If the app structure remains more predictable and consistent to fully duplicate the single and quad calibration flows even for steps that share identical content, duplicate the steps.  
- A predicted component layout for the app may be something like the below:
  - truss-webui/src
    - App.tsx (or a top-level root component included from it) - the top-level component which manages state
    - pages/
      - Main menu page
      - Edit printers page
      - quad-calibration/
        - Quad beam calibration page 1, page 2, ...
      - single-calibration/
        - Single beam calibration page 1, page 2, ...
    - components/
      - Very few reused components
